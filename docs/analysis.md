# 日報を情報分析に使えるかの検討

- 作成日: 2026-11-13
- 対象: daily-log-kit の日報（`docs/log/`）と分析ツール（`files/tools/daily-log-analyze.mjs`）

## 結論

- **使える用途**: 自分の作業の振り返り、作業を再開するときに前回の状況を思い出すこと、判断待ちの棚卸し、PC作業の計画、複数プロジェクトのうち止まっているものを見つけること
- **使えない用途**: 作業量や生産性の評価、他人との比較。コミットしない作業（調べもの、チャット、テストプレイ）が数値に入らないため
- **改善点を洗い出すツール**: 作成済み（9種類の判定）。数値は「確認のきっかけ」として使う
- **セッション開始時の引き継ぎ**: 実装済み（v1.3.0、8章）。次にやること・判断待ちに加え、始める前の準備と、繰り返している作業（効率化の候補）を Claude に渡す
- **次の一手**: RPGMZ_Prototype の `config.json` に準備のルールを書き（SPEC M8）、1か月使ってから判別のしきい値を見直す（SPEC M7）

## 1. 日報ができるタイミング

| タイミング | 何が記録されるか | 仕組み | 自動か |
| --- | --- | --- | --- |
| Claude Code（Web・PC）で作業し、応答を終えるとき | 書き忘れがあれば1回だけ促す | Stop フック | 自動 |
| 作業の終わり・PR を作る前 | 日報メモ（決めたこと、作ったもの、次にやること、判断待ち） | `daily-log` Skill | Claude が書く |
| claude.ai のチャットで決めた日の終わり | 同上（`source: chat`） | 依頼文4 → Claude Code に追加を頼む | 半自動（頼む必要あり） |
| PR のマージ（既定のブランチへの push） | 日報（メモ＋PR＋コミット）と一覧を作り直す | GitHub Actions | 自動 |
| 導入直後に1回 | 全履歴からの過去の日報 | `generate --all` | 自動 |
| 好きなとき（週1回を推奨） | 傾向・改善点・判断待ち | 分析ツール | コマンド1つ |

記録されないもの: Web 版 Claude Code の会話そのもの（要約だけが残る）、claude.ai で頼み忘れた日の決定、コミットしない作業の時間。

使わないと決めたタイミング: Claude Code の `SessionEnd` フック。セッションを止められず、実行時間の上限が既定1.5秒なので、Claude にメモを書かせられない。

## 2. 追跡できる情報と、その確かさ

| 情報 | 細かさ | 確かさ | 理由 |
| --- | --- | --- | --- |
| コミットの日時・件名・変更行数 | 分単位、1件ごと | 高 | Git の記録そのもの（作成者の日時を使うので、amend しても変わらない） |
| PR の番号・題名・マージ日時 | 1本ごと | 高 | マージコミットから取得。スカッシュマージは題名の「(#番号)」から |
| PR の最初のコミットからマージまで | 1本ごと | 中 | マージコミットがある PR だけ。スカッシュマージは測れない |
| 作業日・曜日・時間帯 | 日・3時間ごと | 高 | コミットの日時から |
| 作業のまとまりの回数と推定時間 | 回ごと | 低〜中 | コミットの間隔が2時間以内なら同じ作業とみなす推定。コミットしない作業は入らない |
| 決めたこと・次にやること・判断待ち | メモ1件ごと | 中 | メモの書き方しだい。「決めたこと」はユーザーの承認だけを書く決まり |
| 判断待ちの解決 | — | 低 | 新しいメモに書かれなくなったら解決とみなす（SPEC M2 で改善） |
| 日報メモの記録率 | 日ごと | 高 | 導入日以降、コミットのあった日にメモがあるか |

## 3. 試しに動かした結果

RPGMZ_Prototype の活動ログ（10/31〜11/13）に合わせた作業時間帯・PR・チャット分の日報メモを持つテスト用リポジトリで実行した（実際のリポジトリではない）。

| 指標 | 結果 |
| --- | --- |
| 作業日 | 9日（コミットのある日5日、メモだけの日4日） |
| 作業のまとまり | 8回、約17.7時間（推定） |
| 深夜（0〜4時）のコミット | 29% → 改善点として検出 |
| PR の最初のコミットからマージまで | 約1時間（中央値） |
| 判断待ち | 「ボスの名前（ヴォルクは仮）」（2回のメモに出現）、「30日目の強制開始の有無」 |
| その他の検出 | 放置されたブランチ1本、大きなコミット1件（短編データの一括取り込み → 理由があるので対応不要） |

実際の数値は `node tools/daily-log-analyze.mjs` を RPGMZ_Prototype で実行して確認する。

## 4. 作業の進め方の改善点（今回の開発の振り返り）

| # | 事実 | 影響 | 対策 | 状態 |
| --- | --- | --- | --- | --- |
| 1 | Windows PowerShell 5.1・実際の robocopy・本物の GitHub での確認をしないまま配布した | 利用者の PC で初めて不具合が出る恐れ | Windows の通しテストを CI で毎回実行（`kit-ci.yml`） | 作成済み。初回の実行を確認する（SPEC K1） |
| 2 | 版番号の書き換えや改行コードを手作業で直していた | v1.1.2 の `publish-kit.bat` の改行が LF になっていた（検査で発見） | キットの決まりの検査（`tests/kit.test.mjs`）。publish-kit も反映前に実行 | 作成済み・修正済み |
| 3 | 2日で5回版を上げた（要件が会話の途中で次々に出た） | 利用者が毎回 zip を受け取って反映する手間 | 小さな変更は SPEC にためてまとめる。Claude Code がキットのリポジトリを直接直し、マージで自動リリース（`kit-release.yml`） | 作成済み |
| 4 | 手順が会話ごとに少しずつ変わり、チャットの中に散らばった | どの手順が最新かわからない | マニュアル（`docs/manual/index.html`）と CLAUDE.md に集約 | 作成済み |
| 5 | 公開リポジトリに作品固有の情報（`extras/`）を入れていた | 未公開作品の設定が誰でも読める | v1.2.0 で削除。特定のリポジトリ向けのファイルはそのリポジトリの PR に入れる（ADR 0004） | 削除済み。過去の履歴には残る |
| 6 | RPGMZ_Prototype の作業の一部は 0〜4時（11/02、11/09、11/10） | 深夜のコミットは有意にバグを含みやすいという研究がある | 深夜に作った PR は翌朝に差分を見てからマージする | 運用で対応（分析ツールが毎回知らせる） |
| 7 | PC でしかできないテストプレイ（PR #32 の項目4〜13 など）がたまっている | 作ったものの確認が遅れ、不具合の発見が遅れる | 日報メモで「（PC）」と書き、分析ツールが5件以上で知らせる。PC作業の日を決める | 仕組みは作成済み |
| 8 | claude.ai のチャットで決めたことは自動で残らない | 11/03〜07 の空白のような穴が再び生じる | チャットの終わりに依頼文4を使う習慣。将来は claude.ai のプロジェクトの指示に「終わりに日報メモを出す」と書く | 運用で対応 |

## 5. 分析ツールとしての評価

研究で示されている注意点に合わせて、使い方を決めた。

| 観点 | 根拠 | このツールでの扱い |
| --- | --- | --- |
| 指標は複数の側面で見る | SPACE フレームワークは「少なくとも3つの側面の指標を組み合わせ、1つは本人の感じ方（アンケートなど）を入れる」ことを勧め、活動量の指標だけで判断しないよう注意している | 量（Activity）、流れ（Efficiency）、決定と課題を出す。本人の感じ方（Satisfaction）は未対応 → 日報メモに任意の「手応え」を足す（SPEC M4） |
| 指標は行動を変える | 同じく SPACE は「指標が行動を形づくる」と指摘している | スコアやランキングを作らない（ADR 0007） |
| 変更が届くまでの時間 | DORA の指標「変更のリードタイム」（変更が本番に届くまでの時間） | PR の最初のコミットからマージまで、を近い指標として出す。ゲームの公開（本番）までは測らない |
| 手戻り | DORA の「手戻り率」（障害で予定外の対応をした割合） | 修正コミットの割合を、手戻りの目安として出す（件名の「fix」「修正」から判定する近似） |
| 深夜の作業 | Linux カーネルと PostgreSQL の研究で、0〜4時のコミットは有意にバグを含みやすく、7時〜正午は少ない（相関であり因果ではない） | 深夜率が25%以上で知らせる |

## 6. 分析ツールの提案（推奨順）

| 案 | 内容 | 費用 | 作業量 | 保守性 | U2U 移行への影響 |
| --- | --- | --- | --- | --- | --- |
| **M1 前回の続きを自動で渡す（実装済み）** | SessionStart フックで、次にやること・判断待ち・始める前の準備・効率化の候補を Claude の文脈に入れる（8章） | 0円 | 小 | 高（日報メモの形式に依存するだけ） | なし |
| M2 判断待ちの解決記法 | 「決めたこと」に `解決: <項目>` と書くと判断待ちから外す | 0円 | 小 | 高 | なし |
| M3 週1回の分析を Issue に | Actions で分析を実行し、改善点を Issue にする | 0円（Actions 数十秒/週。公開リポジトリは無料、非公開は月2,000分の無料枠内） | 小 | 中（通知が増える） | なし |
| M4 手応えの記録 | 日報メモに任意の「手応え（1〜5）」「詰まったこと」を足す | 0円 | 小 | 高 | なし |
| M5 ダッシュボード | `--json` の出力を読む HTML 1枚で、複数リポジトリを比較 | 0円 | 中 | 中 | なし |
| M6 PC の会話記録から下書き | `transcripts` の出力から日報メモの下書きを作る | 0円 | 中 | 低（記録の形式が非公式） | なし |

M1 を選んだ理由: 日報を「書く」仕組みはできたが、「読む」のは人の手間だった。SessionStart フックは Claude Code の公式の機能で、文脈を読み込ませる用途が想定されている。前回の続きから自然に始められるので、日報メモを書く動機にもなる。

## 7. 改善点を洗い出すツール（作成済み）

`node tools/daily-log-analyze.mjs` が、9種類の判定で改善点を出す（判定としきい値は `files/docs/specs/daily-log.md` 12.2）。

- 各改善点に「根拠の数値」と「次にやること」を1つずつ付ける
- しきい値は `docs/log/config.json` の `analysis` で変えられる
- 複数のリポジトリを並べると、概要の表でまとめて比べられる
- Claude Code には「作業を分析して」と頼めばよい（`daily-log` Skill の手順C）

## 8. 準備作業と繰り返しの判別（v1.3.0）

### 8.1 セッション開始時に渡すもの

| 項目 | 作業の効率化につながる理由 |
| --- | --- |
| 次にやること＋作業キューの行 | 完了条件と実行場所がその場でわかり、SPEC.md を開いて探す手間がない |
| Web版での「この環境ではできない」の印 | PC でしかできない作業を Web版で頼んで止まる、という空振りを防ぐ |
| 始める前の準備 | `git pull` 忘れ（11/13 の Unity_CharacterTest の衝突の原因）、`npm ci` 忘れ、エディタを開いたままの `game/data` 編集を、作業の前に気づける |
| 効率化の候補 | 手作業の繰り返しを、スクリプトや Skill にする候補として示す |

### 8.2 繰り返しの判別の仕組み

| 種類 | 見つけ方 | 見つかったときの意味 |
| --- | --- | --- |
| 準備作業の繰り返し | 「登録」「起動」「取り込み」「同期」「ビルド」などの言葉が、3日以上の「作ったもの・変えたもの」に出る。対象（プラグイン名など）が違っても数える | 同じ種類の手作業を毎回している。スクリプトか SessionStart フック、準備のルールにする |
| 似た作業の繰り返し | 似ている度合い0.5以上の作業（日報メモとコミットの件名）が3日以上に出る | 同じ手順を何度もしている。Skill か npm スクリプトにする |
| 繰り越し | 同じ「次にやること」が3回以上のメモに、3日以上にわたって出て、最新のメモにも残る | 着手できない理由がある（PC が要る、判断待ち、準備不足） |
| 修正の集中 | 同じファイルへの修正コミットが30日で3回以上 | テストや検査が足りない |

似ている度合いは、日本語でも使えるよう2文字ずつの組の一致率で測り、ひらがな（助詞・送り仮名）を除いた内容の言葉でも比べる。試作の段階で次の2つの問題が見つかり、直した。

- 「C3 の画像1体の取り込み」と「C3 の画像を1体取り込む」が別の作業と判定された（0.33）→ 内容の言葉で比べて一致
- 実装のコミット「D14: CF_EscapeItems」と作業「CF_EscapeItems をプラグイン管理に登録」が同じ作業と判定された → 英字だけの文と日本語の文は、ほぼ同じとき（0.8以上）だけ同じとみなす
- 別のプラグインの登録（「CF_HeroineStatus を登録」と「CF_EscapeItems をプラグイン管理に登録」）は文としては似ていない（0.18）→ 準備作業の言葉の出現日数で拾う

### 8.3 限界

- 文字の重なりによる推定なので、言い回しが大きく違う同じ作業は見逃し、同じ言葉を含む別の作業をまとめることがある
- コミットにも日報メモにも書かれない作業（PC での手作業など）は判別できない。日報メモに書くほど精度が上がる
- しきい値は既定値。1か月運用してから `docs/log/config.json` の `analysis` で調整する（SPEC M7）
