# 日報（日毎ログ）の仕様

- キット: daily-log-kit v1.6.0（どのリポジトリでも同じ内容。作品・製品ごとの差は `docs/log/config.json` だけで吸収する）
- 更新日: 2026-11-10

## 1. 目的

チャット（claude.ai）、Claude Code（Web版・デスクトップ版）、Git の作業を、日ごとに1ファイルへ集める。「いつ・何を決め・何を作り・次に何をするか」を、後から人もAIも同じ場所で読めるようにする。

## 2. 仕組みの全体

| 層 | 誰が書くか | 置き場所 | 中身 |
| --- | --- | --- | --- |
| 日報メモ | Claude Code（Skill）、人 | `docs/log/entries/YYYY-MM-DD/HHMM-件名.md` | 決めたこと・作ったもの・次にやること・未解決 |
| 日報 | `tools/daily-log.mjs`（自動） | `docs/log/YYYY-MM/YYYY-MM-DD.md` | その日の日報メモ＋PR＋コミット |
| 一覧 | `tools/daily-log.mjs`（自動） | `docs/log/README.md` | 日ごとの件数と日報へのリンク |

- メモはセッションごとに別ファイルにする。並行するPRが同じファイルを編集しないので、マージで衝突しない
- 日報と一覧は Git の履歴とメモから毎回作り直す（決定的な出力。同じ入力なら同じ内容）

### 作られるタイミング

| タイミング | 仕組み | 何が起きるか |
| --- | --- | --- |
| Claude Code のセッションを始めるとき | SessionStart フック `.claude/hooks/daily-log-session-start.mjs` | 次にやること・判断待ち・始める前の準備・効率化の候補を Claude に渡す（13章） |
| Claude Code が応答を終えるとき | Stop フック `.claude/hooks/daily-log-reminder.mjs` | 作業の差分があるのに日報メモがなければ、同じ HEAD につき1回だけ記録を促す |
| セッションの終わり・PR作成前 | Skill `.claude/skills/daily-log/SKILL.md` | 日報メモを書き、日報を作り直してコミット |
| 既定のブランチ（main など）への push（PRのマージ） | GitHub Actions `.github/workflows/daily-log.yml` | 直近14日分の日報と一覧を作り直し、変更があればボットがコミット |
| 導入直後に1回 | `generate --all` | 全履歴から過去の日報を作る |
| 好きなとき（週1回を推奨） | `node tools/daily-log-analyze.mjs` | 傾向・改善点・判断待ちの一覧を表示（12章） |

使わないタイミング: Claude Code の `SessionEnd` フックは、セッションを止められず実行時間も短い（既定1.5秒）ため、Claude にメモを書かせる用途には使えない。書き忘れの防止は `Stop` フックで行う。

## 3. 作業日の区切り

- タイムゾーンは `tz`（既定 `Asia/Tokyo`）
- `dayStartHour`（既定 4）より前の時刻は前日に数える。深夜0〜4時の作業を前日の続きとして1日にまとめるため。表示では「翌00:13」のように示す
- 0 にすると暦日どおりになる

## 4. 日報メモの形式

```markdown
---
date: 2026-11-09
time: "02:27"
source: claude-code-web   # claude-code-web / claude-code / chat / pr / manual
branch: feat/last-resort
title: 奥の手の設計確定
---
## 決めたこと
- （ユーザーが決めた・承認したことだけ）
- 解決: ボスの名前 → ヴォルクに決定
## 作ったもの・変えたもの
- （ファイル、作業キュー番号、ADR、PR）
## 次にやること
- （PCでしかできない作業には「（PC）」）
## 未解決・判断待ち
- （判断待ち、未確認の情報）
```

- 中身のない見出しは日報に出ない
- Claude の提案で未承認のものを「決めたこと」に書かない
- 判断待ちが解決したら、「決めたこと」に `解決: <判断待ちの項目>` と書く。`→` の後ろに決めた内容を書いてよい（4.1）

### 4.1 判断待ちの解決（`解決:`）

| 書き方 | 例 |
| --- | --- |
| `解決: <項目>` | `- 解決: 消費MPの値` |
| `解決: <項目> → <決めた内容>`（`->`、`⇒` も可。`：` も可） | `- 解決: ボスの名前 → ヴォルクに決定` |

- `<項目>` は判断待ちの文をそのまま写すのが確実。先頭などの一部（4文字以上）でもよい。判断待ちの文と `<項目>` の一方がもう一方を含めば同じとみなす（記号と空白は無視）
- 解決した判断待ちは、分析（12章）とセッション開始時の引き継ぎ（13章）の判断待ちの一覧から外れる。分析には「解決した判断待ち」として直近の分が出る
- 解決の後のメモにまた同じ判断待ちを書くと、判断待ちに戻る
- 同じメモの「未解決・判断待ち」と「決めたこと」の両方に書いたときは、解決を優先する
- `解決:` を書かなくても、新しいメモに書かれなくなれば、期間（既定7日）を過ぎて一覧から消える
- 秘密情報（トークン、パスワード）と個人情報は書かない。日報は Git に残り、公開リポジトリなら誰でも読める

## 5. 日報の形式（自動生成）

1. 見出し `# YYYY-MM-DD（曜）`
2. 集計表: コミット数（うちマージ）、時間帯、PR数、日報メモ数
3. `## 日報メモ`: メモを時刻順に（見出しは2段下げる）
4. `## PR`: マージコミット（`Merge pull request #N`）とスカッシュ（`題名 (#N)`）から、番号と題名
5. `## コミット`: マージ以外の全コミット（時刻、短いハッシュ、件名）

除外するコミット: 作者が `excludeAuthors`（既定はボット）、件名が `excludeSubjectPattern`（既定はボットの「日報を更新」）に合うもの。

## 6. 設定 `docs/log/config.json`

| キー | 既定値 | 意味 |
| --- | --- | --- |
| `tz` | `Asia/Tokyo` | 集計のタイムゾーン |
| `dayStartHour` | `4` | 作業日の始まりの時刻 |
| `logDir` / `entriesDir` | `docs/log` / `docs/log/entries` | 出力先とメモの置き場所 |
| `baseBranch` | 空（自動） | フックの比較先。空なら origin/HEAD → origin/main → main → master |
| `excludeAuthors` | `["github-actions[bot]"]` | 除外する作者 |
| `excludeSubjectPattern` | `^docs\(log\): 日報を更新` | 除外する件名（正規表現） |
| `defaultDays` | `14` | `generate` で作り直す日数 |

導入スクリプトは既存の設定ファイルを上書きしない。

## 7. コマンド

| コマンド | 用途 |
| --- | --- |
| `node tools/daily-log.mjs generate` | 直近14日の日報と一覧を作り直す |
| `node tools/daily-log.mjs generate --all` | 全期間を作り直す（導入直後、設定変更後） |
| `node tools/daily-log.mjs generate --since 2026-11-01 --until 2026-11-10` | 期間を指定 |
| `node tools/daily-log.mjs generate --dry-run` | 書き込まずに変更予定だけ表示 |
| `node tools/daily-log.mjs new-entry --title 件名 [--date D] [--source S]` | 日報メモの雛形を作る |
| `node tools/daily-log.mjs check` | 日報メモの有無を判定（0=OK、3=なし）。フックが使う |
| `node tools/daily-log.mjs transcripts --since D` | PCの Claude Code の会話記録から、このリポジトリでの依頼文を日別に出す（材料。コミットしない） |
| `node tools/daily-log-analyze.mjs [リポジトリ...] [--since D] [--out F] [--json]` | 分析（12章）。複数のリポジトリを並べるとまとめて比較 |
| `node tools/daily-log-brief.mjs [--env web\|pc]` | セッション開始時の引き継ぎを表示（13章。SessionStart フックが使う） |
| `node --test tools/daily-log.test.mjs tools/daily-log-analyze.test.mjs tools/daily-log-brief.test.mjs` | 単体テスト |

## 8. 過去の分の作り方（バックフィル）

| 情報源 | 取り込み方 | 自動化 |
| --- | --- | --- |
| Git のコミット・PRマージ | `generate --all` | 全自動 |
| マージ済みPRの説明文 | `gh pr list --state merged --json ...` を Claude Code が要約し、マージ日のメモ（`source: pr`）にする | 半自動（Skill の手順B） |
| PCの Claude Code の会話記録 | `transcripts` の出力を要約してメモにする | 半自動。記録の形式は非公式で、既定では30日で削除される |
| Web版 Claude Code のセッション | 会話はリポジトリに残らない。コミットとPR説明文から復元する | 自動部分のみ |
| claude.ai のチャット | 過去チャット検索で拾った内容をメモ（`source: chat`）にする | 半自動（依頼文あり） |

PCの会話記録を残したい場合は、ユーザー設定 `~/.claude/settings.json` の `cleanupPeriodDays` を大きくする（例 365）。0 にすると記録自体が書かれない不具合が報告されているので、0 は使わない。

## 9. ブランチ保護があるとき

GitHub Actions のボットが main に push できない場合は、次のどちらかにする。

1. ワークフローを削除し、日報の生成を Skill の手順（PRの中で `generate` してコミット）だけにする（推奨。設定変更が不要）
2. ルールセットでボットの push を許可する

## 10. 制約と注意

- 依存パッケージなし。Node.js 18 以上
- `git log` は既定でチェックアウト中のブランチ（HEAD）を読む。Actions では main
- 浅いクローンでは古い日が欠ける。ツールが警告を出す
- 日報ファイルの手修正は次の生成で消える。直したい内容はメモに書く
- Stop フックは判定できないときとエラー時に何もしない（作業を止めない）

## 11. 導入・更新・再適用・取り外し

手順は `docs/procedures/daily-log-kit.md`。キットのリポジトリは `Hamm-Coder/daily-log-kit`、マニュアルはその `docs/MANUAL.md`。

## 12. 分析（`tools/daily-log-analyze.mjs`）

日報メモと Git の履歴から、作業の傾向と改善点を出す。出力は Markdown（既定は画面、`--out` でファイル）または JSON（`--json`。他のツールに渡す用）。

### 12.1 わかること

| 区分 | 指標 | 出どころ |
| --- | --- | --- |
| 量と頻度 | 作業日、コミット、PR、日報メモ、週ごとの推移、曜日と時間帯 | Git の履歴、日報メモ |
| 作業時間の目安 | 作業のまとまり（コミットの間隔が2時間以内なら同じ作業）の回数と推定時間 | Git の履歴 |
| 流れ | PRの最初のコミットからマージまでの中央値、放置されたブランチ | マージコミット、リモートのブランチ |
| 品質の兆し | 深夜（0〜4時）のコミットの割合、直近の修正コミットの割合、大きなコミット | Git の履歴 |
| 決定と課題 | 最近の決定、判断待ち（繰り越しの回数つき）、解決した判断待ち（4.1）、次にやること、PCでしかできない作業 | 日報メモの4つの見出し |
| 記録の質 | 日報メモの記録率（仕組みを入れた日以降、コミットのあった日のうちメモがある日の割合） | 日報メモ、Git の履歴 |
| 繰り返し | 似た作業・同じ種類の準備作業の繰り返し、繰り越されている「次にやること」、同じファイルへの修正の集中 | 日報メモ、コミットの件名、修正コミットのファイル |

### 12.2 改善点の判定

| ID | 内容 | 既定のしきい値 |
| --- | --- | --- |
| memo-coverage | 日報メモの書き忘れ | 記録率80%未満（対象3日以上） |
| late-night | 深夜のコミットが多い | 25%以上（10件以上）。深夜のコミットは有意にバグを含みやすいという研究に基づく（Eyolfson et al. 2011） |
| pr-lead-time | PRがマージまで長い | 中央値3日超（3本以上） |
| stale-branches | 放置されたブランチ | main に未マージで14日以上更新なし |
| large-commits | 大きなコミット（情報） | 1000行以上または50ファイル以上（日報とキットのファイル、ロックファイルを除く） |
| fix-ratio | 直近の修正の割合が高い | 直近14日で30%以上（10件以上） |
| pending-carry | 判断待ちの繰り越し | 2回以上のメモに出て、最初から7日以上 |
| pc-tasks | PCでしかできない作業がたまっている | 直近14日のメモの「（PC）」が5件以上 |
| inactive | 作業がない（情報） | 14日以上 |
| repeated-prep | 同じ種類の準備作業の繰り返し（提案） | 「登録」「起動」「取り込み」「同期」「ビルド」などの言葉が、直近60日の3日以上の「作ったもの・変えたもの」に出る（対象が違っても数える） |
| repeated-work | 似た作業の繰り返し（提案） | 似ている度合い0.5以上の作業が、直近60日の3日以上に出る |
| carried-next | 繰り越されている「次にやること」 | 3回以上のメモに3日以上にわたって出て、最新のメモにも残っている |
| fix-hotspot | 同じファイルの修正の集中 | 直近30日で同じファイルへの修正コミットが3回以上 |

似ている度合い: 番号（D14、#26）・数字・記号を除き、2文字ずつの組の一致率で測る。文そのものと、ひらがな（助詞・送り仮名）を除いた内容の言葉の両方で比べて高い方を使う（「画像1体の取り込み」と「画像を1体取り込む」を同じとみなす）。英字だけの文と日本語を含む文は、ほぼ同じとき（0.8以上）だけ同じとみなす。

しきい値は `docs/log/config.json` に `"analysis": { "lateNightRatioMax": 0.3 }` のように書いて変えられる（キー名は `tools/daily-log-analyze.mjs` の `ANALYSIS_DEFAULTS`）。

### 12.3 わからないこと

- コミットしない作業（調べもの、チャット、テストプレイ）の時間。作業時間の推定は下限の目安
- 作業の難しさや成果物の質
- Web版 Claude Code の会話の中身（日報メモに書かれた要約だけが残る）
- `解決:`（4.1）を書かずに済ませた判断待ちが、本当に解決したかどうか（新しいメモに書かれなくなったら一覧から消える）

### 12.4 使い方の決まり

- 数値は自分の作業の傾向をつかむためのもので、成果や生産性の評価には使わない。件数は増やそうとすると中身が薄くなる（SPACE フレームワーク: 活動量の指標を単独で使わない）
- 改善点は「確認のきっかけ」。素材の一括取り込みの大きなコミットのように、理由があれば対応しなくてよい

## 13. セッション開始時の引き継ぎ（`tools/daily-log-brief.mjs`）

Claude Code のセッションを始めると、SessionStart フックが次の4つを Claude の文脈に渡す。前回の続きを毎回説明しなくてよくなる。

| 項目 | 内容 | 出どころ |
| --- | --- | --- |
| 次にやること | 最新の日報メモの「次にやること」。作業キューの番号（例 `D4`）があれば `SPEC.md` の行（作業・成果物・完了条件・実行場所・状態）を添える。Web版では「（PC）」や実行場所が PC の作業に「この環境ではできない」と付ける | 日報メモ、`SPEC.md` |
| 判断待ち | 直近7日のメモの「未解決・判断待ち」（最初に出た日と回数）。`解決:`（4.1）で解決したものは出さない | 日報メモ |
| 始める前の準備 | リポジトリの状態から: 取り込んでいないコミット（`git pull`）、未コミットの変更、`node_modules` がない（`npm ci`）、Git LFS がない、作業中のブランチ。次にやることに合う準備のルール（13.1） | Git、`package.json`、`.gitattributes`、`config.json` |
| 効率化の候補 | 準備作業や似た作業の繰り返し、繰り越し、修正の集中（12.2 の repeated-prep・repeated-work・carried-next・fix-hotspot） | 日報メモ、Git の履歴 |

- 何も出すものがなければ何も出さない
- 速さを優先し、ネットワーク（`git fetch`）は使わない。取り込んでいないコミットは「最後に取得した時点」の数
- 失敗しても何も出さずに終わる（作業を止めない）。止めたいときは環境変数 `DAILY_LOG_SKIP=1`
- 環境は `CLAUDE_CODE_REMOTE` が `true` なら Web版、それ以外は PC

### 13.1 準備のルール（`docs/log/config.json` の `prep`）

次にやることの文に `when`（正規表現）が合うと、`steps` を「始める前の準備」に出す。リポジトリごとの決まった準備（エディタを開く、閉じる、素材を取り込む）を書いておく。

```json
{
  "prep": [
    { "when": "テストプレイ", "steps": ["git pull してから RPG Maker MZ でプロジェクトを開く", "game/data を編集する作業は先にエディタを閉じる"] },
    { "when": "プラグイン管理", "steps": ["プラグイン管理で追加した CF_ プラグインを ON にして保存"] },
    { "when": "Unity|シーン", "steps": ["git pull してから Unity を開く（未追跡の ProjectSettings/ProjectVersion.txt に注意）"] }
  ]
}
```

### 13.2 効率化の候補が出たら

| 候補 | 次にやること |
| --- | --- |
| 準備作業の繰り返し | 手順を1つのスクリプト（例 `tools/setup.ps1`）か Skill にまとめる。毎回のセッションで必要なら SessionStart フックや 13.1 のルールに入れる |
| 似た作業の繰り返し | Skill（`.claude/skills/`）か npm スクリプトにまとめる |
| 繰り越し | 着手できない理由（PC が要る、判断待ち、準備が足りない）を確かめ、作業キューに戻すか分割する |
| 修正の集中 | そのファイルの単体テストか検査を作業キューに追加する |
